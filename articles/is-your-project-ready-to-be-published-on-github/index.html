Is Your Project Ready to Be Published on GitHub, or Is It Exposing Your Secrets Without You Knowing? 🚨

Hamza Bellouch
CEO & Founder of tknoglobal

In the era of AI-assisted coding, creating applications is faster than ever. However, rapid development does not inherently translate into secure deployment. During an audit conducted by our team on software release practices, we observed a striking indicator: approximately one in every three projects reviewed contained exposed sensitive data. Even more concerning, these exposures were not restricted to API keys inside source code—they frequently appeared in assets and artifacts developers never anticipated would be included in the public release.

What Did Our Team's Audit Reveal?

25%

API Keys & Credentials

These secrets can provide unauthorized access to external services or cloud resources, potentially leading to account abuse, compromised infrastructure, or unexpected financial costs.

50%

Images & Screenshots Containing Sensitive Information

Screenshots may expose access tokens, user data, internal information, or details from dashboards that should never be made public.

25%

Internal Code, Permissions & Components

Published releases may reveal internal functionality, code that should not be accessible to ordinary users, or implementation details related to permissions and access control.

These percentages reflect our team's preliminary classification of the observed cases. They are not general statistics representing all GitHub projects.

Where Does AI Fit Into This Problem?

When we ask an AI tool to build an application or prepare a project for release, it may generate files containing information from the development environment or leave unnecessary files in the project package. The problem is not AI itself. The real issue is assuming that the files it generates or selects are ready for publication without a proper review.

How Can We Reduce the Risk of Data Leaks?

1

1. Create a dedicated release build.

Ask your AI tool to prepare a clean, production-ready version in a separate directory from your main development workspace.

2

2. Review files manually.

Inspect source code, configuration files, images, screenshots, and hidden files before publishing anything.

3

3. Never hardcode secrets.

Use environment variables or dedicated secrets-management systems. Add files such as .env to .gitignore where appropriate.

4

4. Scan your repository before pushing.

Use Secret Scanning and Push Protection tools, but do not rely on them exclusively. They may not detect every type of sensitive information.

5

5. Check your Git history, too.

Removing a sensitive file from the latest version does not necessarily remove it from the repository's history.

6

6. If a real secret is exposed, revoke and rotate it immediately.

Do not simply delete the file containing it.

The Key Takeaway

Do not let the convenience of AI-powered development come at the expense of security. Before every release, ask yourself: Does this version contain only what is supposed to be public? Review. Scan. Then publish.

Sometimes, one final review before running git push can make the difference between a successful release and a costly security incident.

What do you think? Should reviewing sensitive files become a mandatory step in every AI-assisted development workflow?
